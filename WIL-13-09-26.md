# Kafka Learning Notes: Admin, Producers, and Partitions

## 1. Kafka Admin & Configuration Control
- Admin configurations can be managed programmatically inside a `main` method, a `CommandLineRunner`, or via explicit Spring beans using `AdminClient`.
- **Why manual configuration matters:** While Spring Boot and `application.properties` automate cluster setup behind the scenes, manual configuration reveals the underlying mechanics of how clients communicate directly with Kafka broker metadata.

## 2. Custom Producer Factory
- Rather than relying on properties like `spring.kafka.producer.key-serializer` and `spring.kafka.producer.value-serializer`, you can explicitly build a custom `ProducerFactory` and `KafkaTemplate` inside a Java `@Configuration` class.
- This provides granular, programmatic control over every parameter (such as `bootstrap-servers`, `acks`, and idempotence) rather than letting Spring infer them.

## 3. Topic Structure & Definitions
- Topic layouts can be configured in depth (specifying partitions and replicas programmatically) using Spring's builder utility:
  ```java
  TopicBuilder.name("NAME_OF_THE_TOPIC").partitions(INT).replicas(INT).build();
  ```

## 4. Partition Creation vs. Partition Routing
- **Partition Creation:** Defines *how many* total lanes (partitions) a topic has. This is set when the topic is created (via `AdminClient` or `TopicBuilder`). Message keys do not control how many partitions are created.
- **Partition Routing:** Decides *which* pre-existing partition a specific message goes into. When you supply a key, Kafka hashes it using the formula:
  $$\text{hash(key)} \pmod{\text{total\_partitions}}$$

## 5. Broker Auto-Creation Behavior
- By default, Kafka brokers run with `auto.create.topics.enable=true`.
- If a producer attempts to send a message to a topic that has not been explicitly created yet, the broker automatically provisions it on the fly using default cluster settings (typically 1 partition and a replication factor of 1).
